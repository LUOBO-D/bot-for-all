# bot-for-all 架构审计与优化方案

日期：2026-11-01
范围：`cmd` 分支单提交 `7d597e0`（M1 群聊 + M2 机器人），后端/前端/迁移/测试全量代码阅读
结论口径：只做审计与建议，不改动业务代码

---

## 0. 总体判断

这份代码**质量高于一般 demo**：seq 事务、SSRF 防护、AES-256-GCM、zod 入参校验、分页上限、XSS 消毒、流式恢复、限流、错误规范化都写对了，75 个后端测试也不是摆设。

真正的问题不在"哪里写错了"，而在**"局部做对了，整体缺了几块面"**：

1. 单实例假设贯穿全局（presence / 队列 / 限流全在内存），但没有一处文档或接口把它显式化；
2. 部署层完全空白（无 Dockerfile / 生产 compose / Nginx / 优雅停机）；
3. 注册模型与最新设计（内部邀请制）冲突；
4. M3 拟人化能力未动工，而它的两个改造点（`context.ts`、`provider.ts`）现在就该预留形状；
5. 文档双版本并存 + 交接说明失效，协作时必然踩坑。

优化原则：**先补"会被未来需求倒逼返工"的接缝，不碰现在跑得好的部分。**

## 2. P0 —— 阻塞项（建议优先处理）

### 2.1 注册模型与最新设计冲突
- 现状：`POST /api/auth/register` + `GET /api/auth/captcha` + `RegisterView.vue`，任何人可注册。
- 设计：仅内部使用，管理员建号 / 一次性邀请码（`invite_codes` 表）。
- 影响：违背"只给内部人用"的产品定位，是最大的设计—实现偏差。
- 方案：新增 `0003_invites.sql`（`invite_codes` 表）→ `POST /api/admin/users`、`POST /api/admin/invites` → 注册接口改为"邀请码激活"（`POST /api/auth/activate`）→ 前端注册页改激活页；`captcha.ts` 与 `svg-captcha` 依赖可退役（内部场景不再需要）。

### 2.2 部署层空白
- 现状：无 Dockerfile、无生产 compose、无 Nginx、无 HTTPS/自签 CA 配置；`docker-compose.dev.yml` 只有 MySQL。
- 影响：只能在开发机跑，无法兑现"国内 VPS 纯 IP 免备案 + 安卓 APK + iPhone PWA"的交付形态。
- 方案：多阶段 `Dockerfile`（前端 build → nginx 静态托管；后端 tsc → node 运行）；`docker-compose.yml`（nginx + app + mysql + redis + searxng）；自签 CA 生成脚本与 Nginx 配置；APK 的 `networkSecurityConfig` 信任该 CA（M4）。

### 2.3 单实例假设未显式化
- 现状：`presence.ts` 进程内 `Map`；`bot/queue.ts` 内存 `Promise` 链 + `Map`；`middleware/ratelimit.ts` 内存计数。
- 影响：不是 bug，但三处都是"上第二实例立即出错"的隐形地雷；且没有接口边界，未来替换要改调用方。
- 方案（低成本，现在就该做）：抽出三个接口 `PresenceStore` / `RateLimiter` / `BotJobQueue`，默认内存实现，Redis 实现留到多实例阶段。**只加抽象、不换实现**，工作量约 1 天，避免 M4 全量返工。
- 同时在 README 写明"当前架构仅支持单实例"。

### 2.4 文档双版本 + 交接说明失效
- 现状：根目录 `2026-10-28-...design.md` 为 269 行旧版；`docs/` 下为 475 行新版；交接说明写"0 骨架待搭建"，与实际不符。
- 方案：以 `docs/` 新版为唯一事实源覆盖根目录旧版并提交；交接说明重写为"当前实现状态 + 本地启动 + 下一步"，或归档到 `docs/archive/`。

### 2.5 无 CI
- 方案：GitHub Actions（私有库每月有免费额度）：`pnpm install --frozen-lockfile` → `tsc` 双端 typecheck → `vitest`（service 起 MySQL 8.4）→ `pnpm build` → 可选 Playwright E2E。单次提交塞了 8,100 行，更需要 CI 兜底回归。

## 3. P1 —— 质量与可维护性（低成本高收益）

| # | 问题 | 证据 | 建议 |
|---|---|---|---|
| 1 | 主进程无优雅停机 | `index.ts` 无 `SIGTERM/SIGINT`；仅脚本里有 `pool.end()` | 加停机钩子：停止接受连接 → 取消在途 bot 任务（ AbortController ）→ 等待流式定稿或标 error → `io.close()` → `pool.end()`；配 `SHUTDOWN_TIMEOUT_MS` |
| 2 | SSE 解析器无 flush | `bot/sse.ts` 只按 `\n\n` 切事件，流尾不足一个空行的事件会丢 | 加 `flush()` 处理残余缓冲；显式忽略 `:` 注释行（心跳）与 `event:`/`id:` 行；补 2 个单测（跨包中文、尾包无空行） |
| 3 | 消息搜索全表扫描 | `services/message.ts:269` 用 `LOCATE(?, m.content)` | 数据量小可接受；到十万级消息时改 `FULLTEXT(ngram)`（与 M3 记忆检索同一方案，一次设计两处复用） |
| 4 | 无管理后台前端 | `frontend/src/views` 只有 4 个页面，管理端只有 API | M4 补 admin 视图：邀请码、账号停用、bot 全局配置、角色卡时间线/回滚、记忆浏览 |
| 5 | 关键验收路径缺测试 | 75 用例集中在 API/bot，E2E 仅 5 个 | 补"断网 30s 重连不丢消息"与"流式中途取消/超时"两个端到端用例（对应设计 M1/M2 验收信号） |
| 6 | Node 版本约束未声明 | README 要求 Node 24，本机 22；`package.json` 无 `engines` | 声明 `engines.node` + `.nvmrc`；实测 Node 22 能否通过全部测试，不行则统一 24 |
| 7 | 迁移无并发锁 | `migrate-core.ts` | 加 `GET_LOCK('chat_migrate')`，防止多实例/CI 并发执行迁移 |
| 8 | 连接池未显式字符集/时区 | `db.ts` | 显式 `charset: 'utf8mb4'`、`timezone: 'Z'`、`connectionLimit` 可配 |
| 9 | 限流/在线状态重启即清零 | 内存实现 | 与 2.3 同一条接口化解决；文档注明"重启后限流窗口重置"可接受 |

## 4. P2 —— 为 M3 预留形状（现在不做，但要按这个形状改）

### 4.1 `context.ts` 改为"装配器"
现状：`buildContext()` 硬编码 `system_prompt + 最近 20 条`。
M3 要插入角色卡、记忆检索、滚动摘要。建议改成：
```
context = assemble([
  personaProvider,      // 角色卡（M3）
  memoryProvider,       // 全文检索 Top-K（M3）
  summaryProvider,      // 滚动摘要（M3）
  recentMessages(20),   // 现有逻辑
])
```
每个 provider 独立可测，M3 只新增 provider、不动主链路。**这是 M3 侵入最小的接缝。**

### 4.2 `provider.ts` 预留 tools 通道
现状只处理 `choices[].delta.content`。M3 需要 function calling：
- 请求侧支持 `tools` / `tool_choice`；
- 流式解析侧支持 `delta.tool_calls`（分片累积 `index` / `function.name` / `arguments`）；
- 对不支持 tools 的供应商静默降级为现有纯文本路径。
建议先补 2 个针对 `tool_calls` 分片的解析单测，再写 Agent 循环。

### 4.3 队列与触发的扩展位
- `trigger.ts` 只有 `mention/all` 布尔判定；M3 需要"companion 的 all 模式先过 speak 决策门"、"快速路径启发式（@/问号/含 bot 名）"。建议把 `shouldTrigger` 升级为返回 `{ trigger, mode: 'fast' | 'companion', reason }` 的判定器，而不是再加布尔分支。
- `queue.ts` 需要支持"主动发言"这类**非消息触发型任务**（目前 `BotJob` 必须带 `trigger: MessageDTO`），建议把 trigger 改为可选。

### 4.4 数据模型新增（按设计 §6，一次迁移到位）
`persona_cards` / `persona_versions` / `bot_memories`（FULLTEXT ngram + 衰减字段）/ `bot_memory_log` / `invite_codes`；`bots` 增加 `persona_level`、`schedule_json`、`proactive` 配置。

## 5. 明确不建议现在做的事

- **不上 Redis**：单实例阶段它只会增加运维面，接口化（2.3）已足够。
- **不换 SQLite**：会破坏 `LAST_INSERT_ID` 连号语义与迁移脚本（交接说明 §3 已警告）。
- **不引入 ORM / NestJS 重写**：现有 `mysql2 + zod` 简单直接，重写无收益。
- **不上向量数据库**：M3 先用 MySQL FULLTEXT，语义检索列二期。
- **不做微服务拆分 / K8s**：几百人内部使用，单体是最优解。
- **不现在做 Markdown 代码块高亮、消息已读回执、图片消息**：均为 M4 或二期，别挤占 M3 工期。

## 6. 本地零成本跑通方案（仅方案，未执行）

环境实测：本机无 MySQL、无 Docker；Node v22.22.2 / pnpm 10.34.5 / OpenSSL 3.5.7；winget 可用；磁盘余量 55G。

**路线：MySQL 8.4 便携版（免安装 ZIP），不装 Docker Desktop。**
- 已验证可下载：`https://cdn.mysql.com//Downloads/MySQL-8.4/mysql-8.4.0-winx64.zip`（HTTP 206，支持断点续传）
- 理由：比 Docker Desktop（需 WSL2、数 GB 下载、常驻后台）轻；与生产同版本 MySQL 8.4，避免方言差异。

步骤（供执行时参考）：
```bash
# 1) 解压到工作区外，例如 C:\dev\mysql-8.4.0；初始化并启动
mysqld --initialize-insecure --datadir=C:\dev\mysql-data
mysqld --port=3306 --datadir=C:\dev\mysql-data   # 前台或注册为本地进程

# 2) 依赖与配置
pnpm install
cp .env.example .env
# 生成 JWT_SECRET / BOT_KEY_SECRET / ADMIN_PASSWORD（openssl rand -hex）

# 3) 初始化
pnpm migrate && pnpm seed:admin

# 4) 启动与验证
pnpm dev        # 后端 :3000，前端 :5173
curl http://127.0.0.1:3000/api/health
pnpm --filter backend test     # 75 用例需要 MySQL 在线
```
可选：`pnpm fake:openai` 起假模型服务做流式联调，零 API 费用；真实模型用本机 Ollama（`ALLOW_PRIVATE_BOT_URLS=true`）。

## 7. 建议推进顺序

| 阶段 | 内容 | 预期产出 |
|---|---|---|
| S0 跑通 | 按 §6 本地启动，跑通 75 测试 + 双浏览器互聊 | 可演示的 M1+M2 |
| S1 补接缝 | P0：文档归一、邀请制、CI、优雅停机、三接口抽象 | 不再被未来需求倒逼返工 |
| S2 M3 数据层 | 新表迁移、context 装配器、provider tools 通道、角色卡 CRUD/回滚 | 大肥鱼"记得住、演得像" |
| S3 M3 调度层 | 作息状态机、主动发言（含防骚扰）、睡眠整理、SearXNG | 大肥鱼"活着" |
| S4 交付 | 生产 compose + Nginx + 自签 CA、管理后台、APK/PWA | 内部上线 |

原则：**S1 的接口抽象必须在 S2 之前完成**，否则 M3 会在内存队列和上下文拼装两处同时积累返工。
